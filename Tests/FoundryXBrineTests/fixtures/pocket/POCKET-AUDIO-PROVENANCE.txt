pocket-fw16-3s.mp3
==================

WHAT IT IS AND WHY IT IS A REAL FILE.

Every Pocket scenario before this one staged its "recording" as `0xFF 0xF3` followed by a run
of 0x41 — two bytes that satisfy the sync-word check and nothing else. That was enough while
the leg stopped at custody, because custody only ever claimed to be holding bytes. It is not
enough now: the leg decodes the audio, and a fixture that is not audio would let a translator
that decodes nothing pass every scenario.

FORMAT — matched to the recorder, not to convenience:

    MPEG-2 Layer III, 32 kbps CBR, mono, 16 kHz, 3.096 s, 12,384 bytes
    first two bytes 0xFF 0xF3 — the exact sync `PocketBLEClient.download` trims to
    12,384 B / 3.096 s = 4,000 bytes/second — the same constant
    `StoredFileDevicePresentation.duration` divides by for fw-1.6

GENERATED BY (deterministic; re-run to reproduce byte-for-byte):

    ffmpeg -f lavfi -i "sine=frequency=440:sample_rate=16000:duration=3" \
           -ac 1 -ar 16000 -f wav tone.wav
    lame -h -m m -b 32 --cbr -q 2 tone.wav pocket-fw16-3s.mp3

    sha256 cd7c286ca980e5a43706243ed7e9fffade4f0d1bc88304452342ca84f454c4d3

THE FILENAME IS UNIQUE ACROSS `fixtures/`, and that is load-bearing rather than tidy: the iOS
test target flattens every non-source file under `Tests/FoundryXBrineTests` into one bundle, so
a second `PROVENANCE.txt` beside `fixtures/device-agnostic/PROVENANCE.txt` fails the build with
"Multiple commands produce ...". `swift test` on macOS never notices; `ci-gates.sh compile`
does.

READ BY REPO PATH, not `Bundle.module` — the same `#filePath`-relative mechanism
`BrineFeatureRunner` uses for `features/`, which is why it is `exclude`d in Package.swift
rather than copied as a resource.

LONGER FIXTURES ARE MADE FROM IT AT RUNTIME. MPEG frames concatenate cleanly, so
`PocketBringOverWorld` repeats this file N times to build a minute of audio rather than
vendoring a second, larger binary.
